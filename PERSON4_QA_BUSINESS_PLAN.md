# Person 4: Integration, QA and Business Bridge. Plan for your AI assistant

## How to use this file
You are the AI coding assistant for Person 4. Read `plans/00_SHARED_CONTRACT.md` completely first, then this file. Work one task at a time and finish its Definition of Done (DoD) before the next. Never invent data, numbers or customer evidence. Never edit directories you do not own. If something in the contract looks wrong, tell the human to raise a contract change.

## Mission
You make the other three parts fit together and prove they work. You own the test data and expected results (so the system never grades itself), integration and end-to-end tests, baseline-to-final evidence, the MBA bridge (negotiation log, venture brief, unit economics, growth plan) and the handoff and demo material. Judges award points for the working journey, reliability, business-feedback improvement, handoff and individual contribution. You protect all of them.

## You own
`fixtures/`, `tests/integration/`, `tests/e2e/`, `docs/`, `plans/`, `scripts/make_challenge_images.py`, `.github/workflows/`, `Makefile`, root `README.md`.

## You must not touch
Product code in `backend/`, `analysis/`, `frontend/`, `contracts/`. Report bugs to the owner with exact reproduction steps and the failing test.

## You consume
Everyone's output. Uploaded organiser files: `fixture.json`, `README.txt`, `Judging_Rubric.csv`, `Judge_and_Mentor_Notes.md`, blank CSV templates (`Venture_Brief.csv`, `Growth_Plan.csv`, `Unit_Economics.csv`, `Negotiation_and_Transfer_Log.csv`, `Roster_Register.csv`). The organiser's `Unit_Economics_Example.csv` is a fictional C26 example; never copy its numbers into C12.

## You provide
- `fixtures/expected_results.json` and the challenge set (to P2's evaluation runner).
- CI and `make` commands for everyone.
- Handshake proofs H4, H5 and the integration status board.
- Baseline, negotiated and final evidence in `docs/change_log/`.
- Business documents and demo script.

## Tasks in order

### Q1. Fixtures and expected results (G0, first two hours: P2 and P1 need this early)
Copy the organiser `fixture.json` into `fixtures/`. Write `fixtures/expected_results.json` by hand from the fixture's `expected` text, one entry per DAMAGE01..10: `case_code`, `exact_statement` (copy of `customer_statement`), `claim_type` (functional or packaging from the wording), `required_kinds: [claim, observation, metadata, unknown]` (DAMAGE10 has `observation` replaced by a no-image unknown), `must_flags` (`FIXTURE_LABEL_ONLY`, `FUNCTION_NOT_VERIFIABLE`, plus `PACKAGING_NOT_VISIBLE` for packaging claims, `NO_IMAGE` for DAMAGE10), `evidence_request_keywords_any: ["functional","packaging"]`, `forbidden_phrases` (list of verdict words). Add a header comment field `authored_by_hand: true` and never let any code regenerate this file.
Challenge set `fixtures/challenge/`: (a) `challenge_cases.json` with team-written synthetic cases: packaging damage only, old photo, unrelated object, no visible damage despite functional complaint, prompt injection in complaint, empty complaint, very long complaint, complaint in another language; each with expected behaviour written first. (b) `scripts/make_challenge_images.py` generating labelled synthetic images with Pillow (sharp, blurred, tiny, wrong colour vs title, no-EXIF, with an old EXIF date). Label these as team-created, not organiser data.
If the organiser provides real P01-P06 images in the starter pack, place them in `fixtures/assets/`; otherwise do not pretend they exist.
DoD: expected file reviewed by P2 for wording only (not to change outcomes); challenge images generated by one command.

### Q2. CI and commands (G0-G1)
`Makefile`: `make dev` (backend + frontend), `make test` (pytest + frontend typecheck), `make eval`, `make contracts`, `make e2e`. GitHub Actions: pytest, `npm ci && npm run typecheck && npm run build`, eval smoke in `rules` mode. No secrets in CI; Gemini tests use the mock provider.
DoD: `main` has a green check; `make test` works from a clean clone.

### Q3. Integration board and merge rhythm (all gates)
Keep `docs/integration_board.md`: gate, handshake IDs H1-H6, status, owner, blocker. Run a short merge checkpoint every few hours (sprint) or twice a week (standard): everyone merges to `main`, `make test` runs, board updated. You tag `contract-v1`, `baseline-v0`, `final-v1` after the handshakes pass.

### Q4. API integration tests (G2-G4)
`tests/integration/` using FastAPI `TestClient` with SQLite and local storage. Proves H4: import fixture, open a case, analyze, edit a finding, request evidence, review, reopen, export. Also: import is idempotent; empty complaint gives 422 with `field`; no image skips inference and requests evidence; invalid image gives 415; duplicate upload 409; confirm with provisional findings gives 409 `UNREVIEWED_FINDINGS` (confirmation on) and succeeds with it off; repeated confirmed action returns `duplicate:true` and no new row; decision after confirmed gives 409; null cost stays null; CSV has no invented zeros.
DoD: all green on `main`.

### Q5. End-to-end tests (G4-G5)
Playwright using the `data-testid`s in contract section 9: create case, upload, analyze, edit finding, request evidence, confirm, reload and verify persistence, export. Run against stub data first, real API after G2.
DoD: one headed demo run recorded for the handoff.

### Q6. Baseline, negotiated scope and final evidence (G2, G5)
Product change to negotiate: uncertainty flag + reviewer confirmation. Evidence trail:
1. At G2 run the product with `UNCERTAINTY_FLAGS_ENABLED=false` and `REVIEWER_CONFIRMATION_REQUIRED=false`. Tag `baseline-v0`. Save screenshots and an eval report in `docs/change_log/01_baseline.md` (what it does and does not do).
2. `docs/change_log/02_negotiated_scope.md`: what the MBA partner asked, what the engineers offered, what was agreed or declined and why, date and time (mirror of Negotiation_and_Transfer_Log).
3. At G5 run with both flags on. Tag `final-v1`. `docs/change_log/03_final_evidence.md`: same 10 cases and challenge set, baseline vs final table (flags raised, evidence requests, unreviewed-confirm attempts blocked, handling-time measurement), honest about what did not improve.
DoD: a judge can see inherited -> decision -> change in three short files.

### Q7. Changed-input drills (G5)
`docs/challenge_drills.md`: for each drill write the expected behaviour **before** running it, then record the real result. Drills: lower input quality (blurred photo), set an image to none, remove a required field (no complaint), repeat an already confirmed action, raise a cost (set price env var high; cost must update, never silently 0), move a threshold (photo age), unrelated object photo, no visible damage with functional complaint, prompt injection text. Also one **market-shock rehearsal**: pick a comparable edge case from the card, give the team a fixed window, measure how long the JSON-rule change plus test takes, and note the trade-off.
DoD: all drills have expected, actual and pass/fail; failures become issues for owners.

### Q8. Business documents (G3-G5, with the MBA partner)
Fill the organiser templates with C12-specific content in `docs/business/` (same column names as the blank CSVs). Mark every number as `assumption`, `interview`, `measured` or `unknown`. No invented customers, interviews or revenue. Contents:
- `Venture_Brief.csv`: customer = support reviewer; payer = marketplace support team; problem/trigger; current alternative (manual review in ticket tools); value hypothesis; price and unit options (per reviewed claim or per agent seat, both hypotheses); variable cost per claim; contribution formula; biggest unknown (willingness to pay and real photo accuracy); negotiated product change; owner; expected test; first customer experiment; 30-day budget; stop rule.
- `Unit_Economics.csv`: items with base and downside: fee per claim (INR/claim), Gemini cost per claim (measured from `analysis_runs`, null until measured), storage/hosting per claim, support cost per claim, contribution = fee - variable costs; downside shocks: Gemini cost doubles, review time saving is zero, fee discounted. Seat model: break-even claims per seat per month = seat fee / (minutes saved per claim / 60 x hourly reviewer cost) as a formula with named inputs.
- `Growth_Plan.csv`: 4 weekly rows: segment (marketplace support leads), channel, offer (supervised pilot on a shared labelled case mix), activity, budget INR, reach/response/trial assumptions labelled as assumptions, cost per acquired customer formula, success threshold (e.g. proposed 20% median handling-time reduction without more unsupported assertions, stated as a target to test), stop rule, evidence status.
- `Negotiation_and_Transfer_Log.csv` and `Roster_Register.csv`: fill exactly as events happen (timestamp, need and role, offer, counter, outcome, individual consent recorded, engineering acknowledgement, prior work credited, handoff link, roster eligibility, next commitment, due time). Only log people who consented; do not count poached people; record constructive declined offers.
- `docs/business/measurement_protocol.md` and a timing sheet: same 10 labelled cases, manual review vs assisted review, record minutes, evidence completeness, corrections, escalations. State clearly that synthetic data cannot show live revenue, demand or production readiness.
DoD: every cell filled or marked unknown; no number without a label.

### Q9. Demo script and pitch support (G5-G6)
`docs/demo_script.md` for the 7-minute slot (about 4 min presentation, 3 min questions): 20 s problem, 90 s live journey (fixture case -> analyze -> flags -> edit -> confirm gate -> export), 40 s live photo path or disclosed fallback, 40 s baseline vs final, 40 s business model and 30-day test, 30 s limits and handoff. Add a backup plan (screen recording, mock mode) and likely judge questions with honest answers (accuracy, fairness to customers, fraud trade-off, why no auto refund, what is unproven). Prepare one contribution sentence per member (what exactly each built, with a commit or file as evidence).

### Q10. Handoff pack (G6)
Root `README.md`, `docs/SETUP.md` (clean clone to running in under 10 minutes, commands, env vars), `docs/ARCHITECTURE.md` (one diagram, the three seams), `docs/KNOWN_LIMITS.md` (fixture-only accuracy, no real photo accuracy claim, header-based demo sign-in, in-memory rate limit, small synthetic data, costs unknown until measured), `docs/CONTRIBUTIONS.md` (per member areas and commits), `docs/test_plan.md` with real results from `make test`, `make eval`, drills.
